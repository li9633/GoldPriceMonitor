- 分支：`dev`
- 日期：2026-11-09
- 环境：Windows / 8 核 / NVMe SSD / Python 3.13.7 / SQLite 3（WAL）
- 压测脚本：`docs/loadtest/`（造数、进程内基准、HTTP 压测、读写争用、定向实验）

## 五、修复验证（同一数据集上实测）

### 5.1 `last_pushed()` 的索引形状 —— 51 倍

不是「加个索引」就行，**形状错了等于没加**：

| 方案 | 执行计划 | p50 |
|---|---|---|
| 现状 `idx_advice_symbol(symbol, created_at)` | `SEARCH ... (symbol=?)` + `USE TEMP B-TREE FOR ORDER BY` | 117.9 |
| 加 `(symbol, status, id DESC)` | 仍走旧索引 + 临时 B 树 | 120.4（**无改善**） |
| 加 `(symbol, id DESC)` | 直接按索引倒序取第一条 | **2.3** |
| 加部分索引 `(symbol, id DESC) WHERE status != 'suppressed'` | 同上 | **2.2** |

建索引耗时 114ms（12 万行），一次性成本。

### 5.2 首页看板 —— 332ms → 0.0ms

`SELECT SUM(c) FROM prices_daily`（732 行）实测 0.0ms。
`get_dashboard_data` 其余三条查询合计 2.4ms。

### 5.3 建议快照 —— 184ms → ~8ms

`MIN` 改从日线表取，实测 0.01ms/次（日线表 732 行），
加上 24h 明细 5.2ms + MA 缓冲 1.0ms。

### 5.4 图表 —— 1,069ms → 毫秒级

日线表已按天聚好，1 年图表变成「查 366 行」。

### 5.5 连接策略 —— 实测几乎无收益（推翻上版猜测）

| 方案 | `get_check_snapshot` p50 |
|---|---|
| 每次新建连接 + 8MB 缓存（现状） | 187.2 |
| 每次新建连接 + 64MB 缓存 | 194.1 |
| 复用连接 + 8MB 缓存 | 180.7 |
| 复用连接 + 64MB 缓存 | 182.3 |

**只有 3% 差异。** 连接开销（约 2ms/次）在 184ms 的扫描面前不值一提。
所以「每 tick 5-6 次连接」「WAL PRAGMA 重复设置」这些优化**优先级应该下调**，
不是瓶颈。

### 5.6 生产代码从不执行 `ANALYZE`

造数时手动执行了 `ANALYZE`，查询计划才稳定走覆盖索引。生产里
`prices` 表持续增长却从不更新统计信息，长期运行后计划有劣化风险。
建议在写入量达到阈值后或每日定时执行一次（`PRAGMA analysis_limit` 可控制成本）。

## 七、PostgreSQL 是否值得切换（用实测数据重算）

> **本节写于优化之前，其中的 PG 倍数是「按索引扫描吞吐推算」的估算。
> 第十一节把 PostgreSQL 真正跑起来实测后，发现这里的估算偏乐观
> （MIN 实际 1.5× 而非 3-6×，看板 COUNT 实际 1.1× 而非 3-5×）。
> 以 §11 的实测为准，本节仅保留当时的推理过程。**

### 7.1 PG 能改善什么

本机索引扫描吞吐实测约 **1,860 万条目/秒**（2.33M 条目 / 125ms）。
PG 的 index-only scan + 并行 worker 在同一台机器上大约是这个的 3-6 倍，
据此估算：

| 瓶颈 | SQLite 实测 | PG 估计 | 日线表方案（实测） |
|---|---|---|---|
| 首页看板计数 | 332ms | 60~110ms | **0.0ms** |
| 建议快照 MIN | 125ms | 25~40ms | **0.01ms** |
| 1 年图表 | 1,069ms | 200~350ms | **~5ms** |
| `last_pushed` | 118ms | 换索引后同样 2ms | **2.3ms（加索引）** |
| 读吞吐天花板 | 18 QPS | 估计 50~100 QPS | 不变 |

### 7.2 PG 明确胜出的唯一场景：多进程写入

这不是推测，是**实测出来的故障**：

- 同时起 3 个写入进程，速率各自 15.8 行/秒，**每个新进程首次写入都会抛
  1 次 `OperationalError: attempt to write a readonly database`**
- 意味着：`uvicorn --workers 2`、或用户误开两个实例、或前后端分离多副本部署，
  会周期性出现写入失败。SQLite 单写者模型是硬边界。

### 7.3 结论

**为了性能：不该换。** 实测的三大瓶颈（332ms / 184ms / 118ms）全部是
「查询写法 + 缺索引 + 缺预聚合」问题，用日线表和一条索引就能消除 95% 以上的成本，
而 PG 只能改善其中一部分，且仍是 O(n)。

**为了多实例/多进程：该换，或改用「单写者 + 读副本」架构。** 目前是单进程单写者，
所以现状安全；一旦要上多 worker，SQLite 的写锁会先出问题（已有实测错误），
这时候迁移就是「被迫且值得」。

顺序建议：先把日线表 + 索引做完（收益最大、风险最低），
把「是否需要多实例」当成独立的产品决策，而不是性能优化的副产品。

## 八、顺带发现的两个非性能问题

1. **未匹配的路径返回 500 而不是 404**
   `app.py` 的 `@app.get("/{full_path:path}")` 兜住了所有路径，
   `frontend/dist` 不存在时 `FileResponse` 抛 `RuntimeError` → 500。
   压测中 `/api/model-pool`（错误路径）就是这样拿到 500 的。
   建议：`/api/*` 未匹配时直接 404，且 `dist` 缺失时给出明确提示。

2. **`frontend/dist` 不存在时根路径 `/` 也 500**
   同上原因。开发环境下单独跑后端会踩到。

# 十一、切换 PostgreSQL 的实测结论（2026-11-09）

不是估算 —— 在本机真的跑起了 **PostgreSQL 16.2**（嵌入式实例，未改动系统环境），
把同一份 630 万行数据用 `COPY` 导进去，建等价索引 + `ANALYZE` + `VACUUM`，
然后逐条对比。

环境：Windows / 8 核 / PG 16.2 / `max_parallel_workers_per_gather=2` /
`shared_buffers=128MB` / 同机对比，SQLite 与 PG 都用**常驻连接**测纯查询时间。

## 11.1 优化后的真实差距（逐条查询）

| 查询 | SQLite | PG 16 | 谁快 |
|---|---|---|---|
| 快照 24h 明细（8640 行） | 4.3ms | 3.6ms | PG 1.1×（基本持平） |
| MA 缓冲（最新 48 条） | 0.02ms | 0.11ms | **SQLite 5×** |
| 日线 MIN（90 天最低价） | 0.01ms | 0.12ms | **SQLite 12×** |
| 最新价 | ~0.005ms | 0.09ms | **SQLite ~18×** |
| 看板总记录数（日线 SUM） | 0.05ms | 0.15ms | **SQLite 3×** |
| 1 年图表（日线 366 行） | 0.05ms | 0.26ms | **SQLite 5×** |
| `last_pushed`（12 万行） | 0.01ms | 0.11ms | **SQLite 11×** |
| `review_stats`（12 万行条件聚合） | 97.0ms | **29.3ms** | **PG 3.3×** |
| `top_failures`（30 万行分组） | 62.0ms | **0.9ms** | **PG 70×** |
| 当天通知计数（30 万行，索引范围） | 3.0ms | **0.8ms** | **PG 3.7×** |
| 全表 `COUNT(*)` | 120ms | 205~221ms | **SQLite 1.7×** |
| 建连接 + 一次查询 | 1.95ms | 26.9ms | **SQLite 14×** |

## 11.2 两条最重要的结论

### ① 小查询上 SQLite 反而快 5~18 倍，因为它没有进程边界

`SELECT price ... LIMIT 1` 这类查询，SQLite 是进程内函数调用（0.005ms），
PG 要付一次本地 TCP 往返（0.09ms）。**这是物理下限，不是调优能消除的。**

而本应用的读路径是「一个请求打十几条小查询」：首页看板一次请求要查价格看板、
AI 统计、通知统计、汇率四段。**每条 +0.1ms，一次请求就 +0.4ms 以上** ——
绝对值不大，但意味着「PG 让首页更快」这个直觉是错的。

### ② 唯一明显变好的是两个统计接口

- `top_failures`：62ms → **0.9ms（70×）**。原因是两个规划器的选择差异 ——
  SQLite 选了 `idx_notify_logs_success(success=?)` 然后建 3 个临时 B 树排序；
  PG 选了 `created_at` 上的 bitmap index scan，直接命中当天的 525 行。
- `review_stats`：97ms → **29ms（3.3×）**，PG 的向量化聚合 + 并行更快。

这两个接口都是 **30 秒轮询**，不是 10 秒轮询的首页。也就是说：
**PG 优化的是「用户偶尔打开的统计页」，而不是「一直在跑的首页」。**

## 11.3 我之前的估算错了两处（实测修正）

| 之前的估算（未实测） | 实测结果 |
|---|---|
| 「MIN 90/180 天 PG 快 3-6 倍」 | 实际 **1.5 倍**（109ms → 73ms），且必须先 `VACUUM` 建立可见性映射 + 建 `INCLUDE (price)` 覆盖索引 |
| 「首页全表 COUNT 分组 PG 快 3-5 倍」 | 实际 **1.1 倍（基本没差别）** —— 324ms vs 306ms |

第二条尤其值得记下来：那个「每 10 秒扫 630 万行」的看板查询，
**换成 PG 也不会变快**。它只能靠预聚合解决 —— 也就是这次做的事。
这也反过来说明：当初「换 PG 能救看板」的想法是错的。

关于 MIN 那条还有个坑：PG 刚批量导入完时索引-only scan 不可用（可见性映射未建立），
规划器会选**并行全表扫描（200ms）**，比 SQLite 的覆盖索引（109ms）还慢；
`VACUUM` 之后才变成 `Parallel Index Only Scan`（73ms）。
**这是迁移后必须纳入运维的事项**（自动 vacuum 会做，但刚导入完的那段时间会退化）。

## 11.4 迁移的硬性前提：必须上连接池

当前代码是「每条查询新建一个连接」（`_session()` 每次 open/close）。
在 SQLite 上这是 1.95ms 的本地开销；**换成 PG 就是 26.9ms**。
按一次请求 10 条查询算，**不做连接池，每个请求要白付约 250ms** ——
比现在所有查询加起来还慢得多。

所以如果要迁 PG，「引入 psycopg_pool / SQLAlchemy 连接池」不是优化项，
而是**前置条件**；顺带 SQLite 这边也该做（实测收益小，但结构一致）。

## 11.5 文本时间列 vs timestamptz

PG 这边把 `call_time` 存成 `timestamptz` 比存成文本快约 1.8 倍
（0.22ms vs 0.39ms），两者都远快于 SQLite 的 3.61ms。差距来自索引范围的
比较方式，不影响架构决策 —— 但迁移时值得顺手把时间列转成原生类型。

## 11.6 结论

**优化之后，为性能迁移 PostgreSQL 的收益已经接近于零，代价却不小。**

| 维度 | 判断 |
|---|---|
| 首页（10s 轮询，最高频） | 25ms，PG 不会更快（小查询反而慢） |
| 建议评估（5 分钟） | 10.5ms，PG 不会更快 |
| 统计页（30s 轮询） | `top_failures` 70×、`review_stats` 3.3× —— **这是唯一实质收益** |
| 全表计数类 | PG 更慢（1.7×） |
| 连接模型 | 必须先上连接池，否则每请求 +250ms |
| 运维 | 多一个服务、要管 VACUUM/统计信息、备份从「复制文件」变成 dump/restore |

**该迁的理由只剩一个（和性能无关）**：需要多进程/多实例写入。
这是实测出来的故障 —— 三个写入进程并发时，每个新进程首次写入都会抛
`attempt to write a readonly database`（见 §7.2），SQLite 的单写者模型是硬边界。

**如果确实要迁，正确的顺序是**：
1. 先上连接池（SQLite/PG 都受益，且是 PG 的前置条件）
2. 再迁数据层，时间列改原生 `timestamptz`，补 `INCLUDE` 覆盖索引
3. 迁完把 `top_failures` / `review_stats` 的收益收下（约 130ms）
4. 别忘了 `VACUUM`/自动 vacuum 的监控

**如果只是想解决那两个统计页的 60~100ms**：给它们加个 30 秒结果缓存
（数据本来就 30 秒才轮询一次）比迁库便宜两个数量级。

## 12.3 重要反转：`top_failures` 的「70 倍」不成立

Windows 那次测出 PG 快 **70 倍**（62ms → 0.9ms），在 Linux 上完全反过来：
**SQLite 0.34ms，PG 1.79ms（SQLite 快 5.3 倍）**。

原因查清楚了 —— 同样的 SQL，两边规划器选了不同索引：

```
[Windows / SQLite]  SEARCH ... USING INDEX idx_notify_logs_success (success=?)
                    USE TEMP B-TREE FOR GROUP BY / group_concat(DISTINCT) / ORDER BY

[Linux / SQLite]    SEARCH ... USING INDEX idx_notify_created (created_at>? AND created_at<?)
                    USE TEMP B-TREE FOR GROUP BY / group_concat(DISTINCT) / ORDER BY
```

当天只有 481 行，正确走 `created_at` 范围索引就是 0.34ms；
Windows 那版选了 `success=0` 的索引，等于把 18 万条失败记录全捞进临时 B 树排序 —— 62ms。

**所以那个 70 倍是「SQLite 在特定环境下挑错索引」的偶然结果，不是 PG 的架构优势。**
结论：不要把那次 70× 当作迁移理由。

## 12.4 跨平台一致的部分（可信度高）

| 对比项 | Windows + PG16 | Ubuntu + PG18 | 结论 |
|---|---|---|---|
| `review_stats` | PG 3.3× | PG 3.3× | **稳定复现**，是真实优势 |
| 180 天 `MIN` | PG 1.5× | PG 1.7× | 稳定复现（但优化后已不需要） |
| 全表 `COUNT GROUP BY` | PG 1.1× | PG 1.2× | 稳定复现（优化后已不存在） |
| 全表 `COUNT(*)` | SQLite 1.7× | SQLite 1.3× | 稳定复现，PG 更慢 |
| 小查询（毫秒级以下） | SQLite 5~18× | SQLite 5~22× | 稳定复现，进程边界开销 |
| 建连接 | SQLite 14× | SQLite 35× | 稳定复现（Linux 上 SQLite 仅 0.10ms） |

两个平台、两个 PG 大版本、完全不同的硬件，这些数字方向一致 —— 说明
「PG 只在重聚合上有优势、在小查询上更慢」是结构性的，不是环境噪声。

## 12.5 结论（与 §11 一致，但更确定）

**优化之后，为性能迁移 PostgreSQL 的净收益接近于零，甚至为负。**

- 首页看板、建议评估、图表、最新价、`last_pushed` —— **全部是 SQLite 更快**，
  因为它们是「一堆毫秒级以下的小查询」，PG 每条约多付 0.1ms 的进程边界成本。
- 唯一稳定胜出的是 `review_stats`（12 万行 × 6 个条件聚合）：49ms → 15ms。
  它挂在建议历史页，**不是前端轮询的热路径**。
- 换来的代价：连接池（必须，否则每请求 +35ms）、VACUUM/统计信息运维、
  `COUNT(*)` 变慢、多一个常驻服务。

**如果只想解决那 49ms**：给 `review_stats` 加 30~60 秒结果缓存，
或者把三个档位的汇总预计算成一张小表，都比迁库便宜两个数量级。

**仍然成立的迁移理由只有一个**：需要多进程/多实例写入 —— SQLite 单写者模型
在并发写入时会直接报 `attempt to write a readonly database`（§7.2 实测）。

## 13.1 高危：日期参数 SQL 注入（已修）

`utils/date_filter.build_date_filter` 把 `start_date` / `end_date` **直接拼进 SQL**，
而这两个参数来自查询串且没有做任何校验：

```python
build_date_filter(start_date="2020-01-01' OR '1'='1")
# → created_at >= '2020-01-01' OR '1'='1'
```

PoC 确认可以：
- 用 `OR '1'='1'` 短路过滤条件，读到本不该返回的数据；
- 用 `' UNION SELECT ...` 拼出可执行子句（实测能跑通，结果被正常返回）——
  配合列数对齐可以读同库其他表（API Key、邮箱密码都在同一个库里）。

**修复**：在唯一汇聚点做严格校验，只接受 `YYYY-MM-DD`，并用 `date(y, m, d)`
拒绝 `2026-13-45` 这类不存在的日期；校验通过后字符串里只可能出现数字和短横线。
同时把校验下沉到 `utils/time_utils.parse_date`，覆盖价格库、汇率库那些
**不走 date_filter** 的日期路径（这些路径原先遇到非法日期直接 500）。

- 非法日期 → **HTTP 400**（`InvalidDateError` + 全局异常处理器），不再是 500
- 空串 `?start_date=` 视为「没传」（前端清空日期框不会报错）
- `time_column` 增加标识符校验，防止列名注入

验证：6 个日期接口 × 非法/注入输入全部 400，合法输入全部 200。

## 13.5 优化遗漏：`/advice/now` 把上下文算了两遍（已修）

```python
record = self.generate(...)            # 内部 build_context（第 1 次）
ctx = self.build_context(...)          # 又算一遍（第 2 次）
```

上下文里包含一次价格快照（实测 10.5ms）和一次建仓回测。现在 `compute()`
接受可选的 `context`，`now()` 只构建一次。加了回归测试锁住调用次数。

## 13.6 优化遗漏：统计信息从不刷新（已修）

`sqlite_stat1` 只在建表时算过一次，表长到几十万行后规划器可能挑错索引 ——
Windows 上实测同一句 `top_failures`：选对索引 0.34ms、选错 **62ms（差 180 倍）**。

新增 `SQLiteMapper.optimize()`（`PRAGMA optimize`，必要时才真正 ANALYZE），
挂在监控循环的每日定时任务上，覆盖 prices / advice / portfolio 三个库。

## 13.7 优化遗漏：日志接口每次全文件扫描（已修）

`total_lines` 必须扫完整个文件才能得出。实测 10 MB（轮转上限）日志：
无过滤 10.9ms、**带级别过滤 70.2ms**，而前端日志页每 10 秒轮询一次。

加了按 `(路径, 大小, mtime_ns, 过滤条件)` 的结果缓存（只保留最近 8 条）：
重复请求 **17.6ms → 0.08ms**、**57.4ms → 0.09ms**；文件追加后正确失效
（实测计数 10 → 15）。

## 13.8 开发环境隐患：跑测试会写真实数据库（已修）

`test_sales.py` 会 `import app`，而 `app.py` 模块级就 `import controller.*`，
各控制器又是 `service = XxxService()` 模块级单例 —— 构造时立刻对
`config` 里的路径建表建索引。**于是跑一次 pytest 就会改动 `backend/data/`**；
真实库有数据时还会触发日线表全量重建（630 万行约 5 秒）。

`test/conftest.py` 现在在导入任何 mapper 之前把四个库路径重定向到临时目录。
验证：跑完 486 个测试后，`backend/data/*.db` 的 mtime 完全没变。

## 13.9 审计过、确认没问题的地方

| 检查项 | 结论 |
|---|---|
| 其余 SQL 拼接 | `symbol`/`id`/分页参数全部是 `?` 绑定；`price_t{horizon}` 的 horizon 有白名单校验 |
| 列名注入 | `date_filter` 增加 `time_column.isidentifier()` 校验 |
| 前端 XSS | 无 `v-html` / `innerHTML`，Vue 默认转义 |

| 连接泄漏 | 已有 `test_sqlite_connections` 覆盖，改动后仍通过 |
| CORS | 未开启，默认同源 |
